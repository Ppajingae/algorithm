# 1일 1코테 개발일지 — 단속카메라

## 문제

**프로그래머스 - 단속카메라**

각 차량은 고속도로의 특정 구간을 이동한다.

```text
[진입 지점, 진출 지점]
```

모든 차량이 최소 한 번 이상 카메라를 만나도록 할 때 필요한 **최소 카메라 개수**를 구하는 문제다.

예제:

```java
int[][] routes = {
    {-20, -15},
    {-14, -5},
    {-18, -13},
    {-5, -3}
};
```

결과:

```java
2
```

---

# 1. 첫 접근

문제를 처음 봤을 때 어떤 알고리즘을 사용해야 할지는 바로 떠오르지 않았다.

먼저 입력 크기를 확인했다.

```text
차량 수 ≤ 10,000
```

모든 차량을 기준으로 다른 모든 차량을 확인하면:

```text
10,000 × 10,000
= 100,000,000
```

수준이 될 수 있다.

따라서 처음부터:

```text
이중 for문으로 모든 차량을 서로 비교하는 것은
조금 위험할 것 같다.
```

라고 판단했다.

그리고 차량의 구간이 주어져 있으므로:

```text
정렬을 먼저 하면 어떨까?
```

라는 생각을 했다.

---

# 2. 첫 번째 생각 — 진입점 기준 정렬

처음에는:

```java
routes[i][0]
```

즉 `start`를 기준으로 정렬하는 방법을 생각했다.

예제:

```java
{
    {-20, -15},
    {-18, -13},
    {-14, -5},
    {-5, -3}
}
```

이렇게 왼쪽부터 차량을 확인하면서 겹치는 차량을 묶으려고 했다.

---

# 3. boolean[]으로 처리 여부를 저장하려고 함

다음으로 생각한 방식은:

```text
첫 번째 차량을 기준으로
뒤 차량들을 검사

↓

같은 카메라로 처리할 수 있으면
처리 완료 표시

↓

boolean[]에 처리 여부 저장

↓

처리되지 않은 차량만 다시 검사
```

하는 방식이었다.

예를 들면:

```java
boolean[] checked = new boolean[routes.length];
```

같은 상태를 두고:

```text
true
→ 이미 카메라에 잡힌 차량

false
→ 아직 처리해야 하는 차량
```

으로 관리하는 방식이다.

---

# 4. 이 접근의 문제

이 방식은 결국:

```text
현재 차량
×
뒤의 여러 차량
```

을 반복해서 확인하게 된다.

최악의 경우:

```text
9999
+ 9998
+ 9997
+ ...
+ 1
```

정도의 비교가 발생한다.

대략:

```text
10,000 × 9,999 / 2
≈ 50,000,000
```

번이다.

그리고 더 큰 문제는 상태 관리였다.

예를 들어:

```text
1번 차량 → 기존 카메라로 처리 가능

2번 차량 → 처리 불가능

3번 차량 → 다시 기존 카메라로 처리 가능
```

같은 상황이 생길 수 있다.

그러면:

```text
어떤 카메라를 기준으로 판단해야 하지?

2번 차량은 어떻게 다시 관리하지?

처리된 차량을 따로 기억해야 하나?
```

같은 문제가 생긴다.

즉 `start` 기준으로 단순하게 정렬한 것만으로는 현재 차량에 대한 판단을 바로 확정하기 어려웠다.

---

# 5. 관점 변경 — 진출점을 기준으로 정렬

여기서 중요한 기준을 바꿨다.

차량:

```text
[-20, -15]
```

을 반드시 잡아야 한다면 카메라를 설치할 수 있는 위치는:

```text
-20 ~ -15
```

이다.

그중:

```text
-15
```

는 이 차량을 잡을 수 있는 **가장 오른쪽 위치이자 마지막 위치**다.

따라서:

```text
가장 먼저 고속도로에서 빠져나가는 차량부터 처리하고

그 차량의 진출점에 카메라를 설치한다.
```

라는 방식으로 바꿨다.

---

# 6. 진출점 기준 정렬

Java에서는:

```java
Arrays.sort(
    routes,
    (a, b) -> Integer.compare(a[1], b[1])
);
```

을 사용했다.

예제는:

```java
{
    {-20, -15},
    {-18, -13},
    {-14, -5},
    {-5, -3}
}
```

순서가 된다.

진출점만 보면:

```text
-15
-13
 -5
 -3
```

순서다.

---

# 7. 첫 번째 카메라 설치

가장 먼저 진출하는 차량:

```text
[-20, -15]
```

을 반드시 잡아야 한다.

이 차량의 진출점:

```text
-15
```

에 카메라를 설치한다.

```java
int answer = 1;
int endPoint = routes[0][1];
```

현재 상태는:

```text
camera = -15
answer = 1
```

이다.

---

# 8. 왜 진출점에 설치하는가?

첫 차량이:

```text
[-20, -15]
```

이라면 다음 위치 모두 첫 차량을 잡을 수 있다.

```text
-20
-19
-18
-17
-16
-15
```

그런데 앞으로 등장하는 차량은 진출점 기준으로 정렬되어 있다.

따라서 가능한 한 오른쪽에 설치하는 것이 이후 차량과 겹칠 가능성을 가장 많이 남긴다.

예를 들어 다음 차량이:

```text
[-18, -13]
```

이라면:

```text
camera = -20
```

은:

```text
[-18, -13]
```

에 포함되지 않는다.

하지만:

```text
camera = -15
```

는:

```text
-18 <= -15 <= -13
```

이므로 두 차량을 동시에 처리한다.

따라서 현재 차량을 처리해야 한다면:

```text
현재 차량의 진출점에 카메라 설치
```

라는 선택을 한다.

---

# 9. 다음 차량 처리

현재 카메라:

```text
endPoint = -15
```

다음 차량:

```text
[-18, -13]
```

이라면:

```text
-18 <= -15 <= -13
```

이므로 이미 처리된다.

코드에서는:

```java
if (endPoint >= route[0]) {
    continue;
}
```

로 확인할 수 있다.

진출점 기준으로 정렬되어 있기 때문에 현재 차량의 `route[1]`은 기존 `endPoint`보다 작아질 수 없다.

따라서 사실상:

```text
route[0] <= endPoint
```

만 확인하면 된다.

---

# 10. 기존 카메라로 처리할 수 없는 경우

다음 차량이:

```text
[-14, -5]
```

라면:

```text
camera = -15
```

이므로:

```text
-15 < -14
```

이다.

즉:

```text
camera
   ↓
  -15

       -14 ---------------- -5
       ↑
     start
```

기존 카메라는 현재 차량의 구간 밖에 있다.

따라서 새로운 카메라가 반드시 필요하다.

이때 다시 현재 차량의 가장 오른쪽 위치:

```text
route[1]
```

에 설치한다.

```java
answer++;
endPoint = route[1];
```

결과:

```text
camera = -5
```

가 된다.

---

# 11. 경계조건에서 발생한 실수

초기 구현에서는:

```java
if (endPoint > route[0]) {
    continue;
}
```

를 사용했다.

하지만 문제 조건에는:

```text
차량의 진입 지점 또는 진출 지점에
카메라가 설치되어 있어도
카메라를 만난 것으로 간주한다.
```

라고 되어 있다.

예를 들어:

```java
int[][] routes = {
    {-10, -5},
    {-5, 0}
};
```

카메라가:

```text
-5
```

에 있다면 두 차량 모두 처리된다.

따라서:

```text
endPoint == route[0]
```

도 기존 카메라로 처리 가능한 경우다.

조건은:

```java
endPoint >= route[0]
```

이어야 한다.

---

# 12. 초기 카메라 개수 실수

처음에는:

```java
int answer = 0;

int endPoint = routes[0][1];
```

로 작성했다.

하지만:

```java
endPoint = routes[0][1];
```

이라는 것 자체가 이미:

```text
첫 번째 차량의 진출점에
카메라 하나를 설치했다.
```

라는 의미다.

따라서 초기 상태는:

```java
int answer = 1;
int endPoint = routes[0][1];
```

이어야 한다.

---

# 13. 최종 코드

```java
public int solution(int[][] routes) {

    int answer = 1;

    Arrays.sort(
        routes,
        (a, b) -> Integer.compare(a[1], b[1])
    );

    int endPoint = routes[0][1];

    for (int[] route : routes) {

        if (endPoint >= route[0]) {
            continue;
        }

        answer++;
        endPoint = route[1];
    }

    return answer;
}
```

조금 더 조건의 의미가 직접적으로 보이도록 쓰면:

```java
public int solution(int[][] routes) {

    int answer = 1;

    Arrays.sort(
        routes,
        (a, b) -> Integer.compare(a[1], b[1])
    );

    int camera = routes[0][1];

    for (int[] route : routes) {

        if (camera < route[0]) {
            answer++;
            camera = route[1];
        }
    }

    return answer;
}
```

의미는:

```text
현재 차량의 진입점이
마지막 카메라보다 오른쪽이다.

↓

현재 차량은 기존 카메라를 만나지 못한다.

↓

새로운 카메라 설치
```

이다.

---

# 14. 시간 복잡도

차량 수를 `N`이라고 하면:

## 정렬

```java
Arrays.sort(routes, ...);
```

객체 배열 형태의 행들을 정렬하므로 전체적으로:

```text
O(N log N)
```

으로 볼 수 있다.

## 순회

```java
for (int[] route : routes)
```

모든 차량을 한 번씩 확인하므로:

```text
O(N)
```

따라서 전체:

```text
O(N log N) + O(N)
```

즉:

```text
O(N log N)
```

이다.

최대:

```text
N = 10,000
```

이므로 충분하다.

처음 생각했던 이중 for 방식:

```text
O(N²)
```

보다 훨씬 효율적이다.

---

# 15. 공간 복잡도

직접 추가한 핵심 상태는:

```java
int answer;
int camera;
```

뿐이다.

처음 생각했던:

```java
boolean[] checked
```

도 필요하지 않다.

알고리즘 자체에서 별도의 차량 상태 배열을 만들지 않으므로 추가 상태는 매우 작다.

# 그리디 알고리즘

## 1. 그리디란?

**Greedy Algorithm / 탐욕 알고리즘**

그리디의 핵심 아이디어는:

```text
현재 상황에서
가장 유리하다고 판단되는 선택을 한다.
```

그리고 그 선택을 계속 반복해서 전체 답을 만든다.

쉽게 말하면:

```text
지금 할 수 있는 최선의 선택을 한다.
```

이다.

하지만 여기서 굉장히 중요한 점이 있다.

```text
현재 가장 좋아 보이는 것을 고른다
=
항상 정답
```

은 아니다.

---

# 2. 그리디가 항상 가능한 것은 아니다

예를 들어 돈을 만들 때:

```text
동전 = 500, 100, 50, 10
```

같은 체계에서는 큰 동전부터 사용하는 방식이 잘 동작한다.

하지만 동전 종류가 임의로:

```text
1, 3, 4
```

이고:

```text
6
```

을 만들어야 한다고 하자.

큰 것부터 고르면:

```text
4 + 1 + 1
= 3개
```

이다.

하지만 최적해는:

```text
3 + 3
= 2개
```

이다.

즉:

```text
현재 가장 큰 것을 선택
```

이라는 지역적인 최선이 전체 최적해를 보장하지 않는다.

그래서 그리디 문제에서 진짜 어려운 부분은:

```text
그리디를 구현하는 것
```

보다는:

```text
왜 지금 이 선택을 해도
최적해를 잃지 않는가?
```

를 찾아내는 것이다.

---

# 3. 이번 문제의 Greedy Choice

이번 문제에서 한 선택은:

```text
가장 먼저 진출하는 차량의
진출점에 카메라를 설치한다.
```

이다.

즉:

```java
Arrays.sort(routes, (a, b) ->
    Integer.compare(a[1], b[1])
);
```

한 다음:

```java
camera = route[1];
```

을 선택한다.

이게 이번 문제의 **Greedy Choice**다.

---

# 4. 왜 이 선택이 안전한가?

진출점이 가장 빠른 차량을:

```text
A = [start, end]
```

라고 하자.

이 차량을 처리하려면 어차피 카메라 하나가:

```text
start <= camera <= end
```

안에는 있어야 한다.

즉 `A`를 처리하는 카메라는 반드시:

```text
|----------------------|
start                  end
```

여기 어딘가에 있어야 한다.

그런데 앞으로의 다른 차량까지 최대한 처리하고 싶다.

그러면 카메라를 가능한 가장 오른쪽인:

```text
end
```

에 밀어놓는다.

```text
|----------------------●
start                  end
                       camera
```

이렇게 하면 현재 차량은 확실히 처리하면서, 오른쪽에서 시작하는 다음 차량들과 겹칠 가능성을 최대한 남긴다.

---

# 5. 왜 더 왼쪽에 둘 필요가 없는가?

예를 들어:

```text
현재 차량
[-20, -15]
```

을 잡기 위해 어떤 최적해가:

```text
camera = -18
```

에 설치했다고 가정하자.

그런데 우리는:

```text
camera = -15
```

로 옮기려고 한다.

현재 차량은 여전히 잡힌다.

그리고 현재 차량이 **가장 먼저 진출하는 차량**이므로 이후 차량들의 진출점은 모두:

```text
>= -15
```

이다.

따라서 기존 카메라 `-18`에 걸리던 이후 차량이 있다면 그 차량의 시작점은:

```text
<= -18
```

이고 진출점은:

```text
>= -15
```

이다.

즉 그 차량은 `-15`도 지나간다.

따라서 카메라를:

```text
-18 → -15
```

로 오른쪽으로 옮겨도 잡고 있던 차량을 잃지 않는다.

이게 이번 그리디 선택이 안전한 이유다.

---

# 6. 그리디에서 정렬이 자주 등장하는 이유

그리디 문제에서는 정렬이 자주 같이 등장한다.

이유는 단순하다.

입력 순서가:

```text
A
B
C
D
```

라고 해서 그 순서가 최적의 판단 순서라는 보장이 없다.

이번 문제도 입력 순서대로 보면:

```java
{
    {-20, -15},
    {-14, -5},
    {-18, -13},
    {-5, -3}
}
```

판단하기 까다롭다.

하지만 진출점으로 정렬하면:

```java
{
    {-20, -15},
    {-18, -13},
    {-14, -5},
    {-5, -3}
}
```

가 되고:

```text
가장 급한 차량부터 처리
```

할 수 있게 된다.

즉 정렬은:

```text
Greedy Choice를 하기 좋은 순서로
입력을 재배치하는 역할
```

을 하는 경우가 많다.

---

# 7. 그리디 문제를 볼 때 생각할 것

앞으로 최소/최대 문제를 봤다고 바로:

```text
이거 그리디인가?
```

하고 알고리즘 이름부터 맞히려고 할 필요는 없다.

대신 다음 질문을 해보는 게 좋다.

```text
1. 현재 하나를 선택해야 한다면
   어떤 선택이 가장 유리한가?

2. 한번 한 선택을 나중에 되돌릴 필요가 있는가?

3. 입력을 정렬하면
   현재 판단을 확정할 수 있는가?

4. 현재의 최선 선택이
   미래의 더 좋은 선택을 막지는 않는가?

5. 이전에 처리한 데이터를
   다시 확인할 필요 없이 버릴 수 있는가?
```

이번 문제는 특히:

```text
정렬 후 현재 판단을 확정할 수 있는가?
```

가 중요했다.

# 8. 이번 문제에서 boolean[]이 사라진 이유

처음에는:

```java
boolean[] checked;
```

가 필요하다고 생각했다.

이건 결국:

```text
과거 차량의 상태를 계속 기억해야 한다.
```

는 모델이었다.

하지만 진출점으로 정렬하고 Greedy Choice를 사용하면:

```text
현재 카메라로 처리된 차량
→ 앞으로 다시 볼 필요 없음
```

이 된다.

따라서 필요한 상태는:

```java
int camera;
```

하나로 줄어든다.

이건 지금까지 코테에서 계속 나온 패턴과도 연결된다.

```text
처음 생각
→ 많은 상태를 저장

문제 구조 파악
→ 필요한 상태만 저장
```

이번에는:

```text
boolean[N]
```

에서:

```text
마지막 카메라 위치 1개
```

로 줄었다.

# 10. 이번 문제에서 잘한 점

### 입력 크기를 보고 이중 for문을 먼저 의심함

```text
N ≤ 10,000
```

을 보고 처음부터:

```text
O(N²)은 위험하지 않을까?
```

라고 생각했다.

복잡도 개선에서 중요한 습관이다.

### 정렬을 스스로 떠올림

처음 정렬 기준은 `start`였지만:

```text
구간 문제

```

라는 방향 자체는 좋았다.

### boolean[]을 고민했지만 최종적으로 제거

처음에는 처리 상태를 전부 저장하려고 했지만 최종적으로:

```java
int camera;
```

하나로 상태를 줄였다.

### 경계조건 수정

```java
endPoint > route[0]
```

에서:

```java
endPoint >= route[0]
```

로 수정했다.

```text
진입/진출 지점에 카메라가 있어도 인정
```

조건을 코드에 정확히 반영했다.

# 12. 그리디와 DP의 느낌 차이

앞서 풀었던 정수 삼각형 DP와 비교하면 차이가 잘 보인다.

## DP

```text
여러 선택 결과가 같은 상태로 합쳐짐

↓

그 상태까지의 최적 결과를 저장

↓

이전 결과를 이용해 다음 결과 계산
```

정수 삼각형에서는:

```text
dp[i][j]
=
해당 위치까지 도달하는 최대 합
```

을 저장했다.

## Greedy

```text
현재 최선의 선택을 확정

↓

이전 선택을 다시 고려하지 않음

↓

다음 문제로 진행
```

이번 문제에서는:

```text
가장 먼저 끝나는 차량의 끝에 카메라 설치

↓

이 선택을 확정

↓

이미 처리된 차량은 다시 보지 않음
```

이다.

간단하게 느낌을 잡으면:

```text
DP
→ 여러 가능성을 압축해서 기억한다.

Greedy
→ 하나의 선택을 확정하고 버린다.
```

정도로 볼 수 있다.

물론 실제 문제에서는 둘을 구분하려면 그 선택이 최적해를 보장하는지 확인해야 한다.

# 13. 앞으로 그리디 냄새를 맡는 기준

다음 특징들이 보이면 그리디를 후보로 생각해볼 수 있다.

```text
최소 / 최대를 요구한다.

정렬하면 순차적으로 판단할 수 있을 것 같다.

현재 하나를 선택하면
일부 입력을 완전히 처리했다고 확정할 수 있다.

처리한 입력으로 다시 돌아갈 필요가 없다.

현재 가장 유리한 선택을 반복하는 규칙이 보인다.
```

하지만:

```text
"최솟값 문제니까 Greedy"
```

처럼 바로 결정하면 안 된다.

항상:

```text
이 선택을 지금 확정해도
나중에 후회할 일이 없는가?
```

를 확인해야 한다.

# 14. 오늘의 핵심 패턴

이번 문제에서 가장 가져갈 만한 사고방식은:

```text
모든 원소를 서로 비교하려고 하지 않는다.

↓

정렬해서 판단 순서를 만든다.

↓

현재 판단을 확정할 수 있는
정렬 기준을 찾는다.

↓

현재 최선의 선택을 한다.

↓

처리된 과거는 버린다.
```

이다.

그리고 구간 문제에서:

```text
[start, end]
```

가 주어졌다면 무조건 `start`만 보지 말고:

```text
start 기준 정렬?

end 기준 정렬?

어느 쪽이 현재 판단을 확정시켜주는가?
```

를 둘 다 생각해볼 가치가 있다.

# 최종 정리

## 알고리즘

```text
Greedy Algorithm
+
Sorting
```

## Greedy Choice

```text
진출점이 가장 빠른 차량의
진출점에 카메라를 설치한다.
```

## 필요한 상태

```text
마지막 카메라 위치
카메라 개수
```

## 시간 복잡도

```text
정렬 : O(N log N)
순회 : O(N)

전체 : O(N log N)
```

## 처음 생각한 방식

```text
start 정렬
+
이중 반복
+
boolean[] 처리 상태 관리
```

## 최종 방식

```text
end 정렬
+
한 번 순회
+
마지막 카메라 위치만 저장
```

## 이번에 새로 가져갈 개념

```text
- Greedy Algorithm의 기본 개념
- Greedy는 단순히 "당장 큰 것/작은 것 선택"이 아님
- 현재 선택이 전체 최적해를 깨지 않는다는 근거가 필요함
- 정렬은 Greedy Choice를 가능하게 만드는 중요한 도구
- 구간 문제에서는 start와 end 중 어떤 기준이 판단을 확정시키는지 확인
- 이미 처리한 데이터를 다시 볼 필요 없도록 문제를 구성할 수 있는지 확인
- 필요한 상태만 저장
```
