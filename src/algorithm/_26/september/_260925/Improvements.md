# 2026-09-25 코딩테스트 복기 - 하노이의 탑

## 문제

프로그래머스 - 하노이의 탑

### 핵심 조건

- 기둥은 `1`, `2`, `3` 총 3개
- 처음에는 모든 원판이 1번 기둥에 존재
- 최종적으로 모든 원판을 3번 기둥으로 이동
- 한 번에 하나의 원판만 이동 가능
- 큰 원판을 작은 원판 위에 올릴 수 없음
- 최소 횟수로 이동해야 함
- `n ≤ 15`

반환해야 하는 것은 각 원판의 실제 크기가 아니라:

```text
[출발 기둥, 도착 기둥]
```

의 이동 순서다.

---

# 처음 접근

문제를 처음 봤을 때 `Stack` 자료구조가 떠올랐다.

하노이 탑의 각 기둥이 실제로 Stack과 유사하기 때문이다.

예를 들어 `n = 3`이라면:

```text
Stack 1     Stack 2     Stack 3

   1
   2
   3
 ─────
```

처럼 생각할 수 있다.

Java로 표현한다면:

```java
Stack<Integer> one;
Stack<Integer> two;
Stack<Integer> three;
```

형태로 만들 수 있다.

원판을 이동할 때도:

```text
목적지 Stack이 비어 있다
→ 이동 가능

목적지의 top > 현재 원판
→ 이동 가능

목적지의 top < 현재 원판
→ 이동 불가능
```

처럼 검사할 수 있다고 생각했다.

조건으로 표현하면 대략:

```java
target.isEmpty() || target.peek() > disk
```

형태가 된다.

---

# Stack 접근에서 생긴 문제

Stack은 현재 퍼즐의 상태를 표현하는 데는 적합하다.

하지만 다음 문제가 생긴다.

```text
현재 이동 가능한 곳이 여러 개라면
어디로 이동해야 최소 횟수가 되는가?
```

예를 들어 첫 번째 원판은 상황에 따라:

```text
1 → 2
```

도 규칙상 가능하고:

```text
1 → 3
```

도 규칙상 가능하다.

Stack을 사용하면:

```text
이 이동이 가능한가?
```

는 판단할 수 있지만:

```text
어떤 이동을 선택해야 최소해가 되는가?
```

는 알려주지 않는다.

즉 Stack은:

```text
문제의 상태를 표현하는 자료구조
```

로는 자연스럽지만:

```text
최소 이동 순서를 생성하는 핵심 알고리즘
```

은 아니었다.

---

# 직접 시뮬레이션

그래서 작은 n부터 직접 움직여봤다.

## n = 1

움직이는 원판:

```text
1
```

이동 횟수:

```text
1
```

---

## n = 2

움직이는 원판 번호:

```text
1 2 1
```

이동은:

```text
1 → 2
1 → 3
2 → 3
```

총:

```text
3회
```

---

## n = 3

직접 시뮬레이션했을 때 움직이는 원판 번호:

```text
1 2 1 3 1 2 1
```

총:

```text
7회
```

여기서 패턴이 보이기 시작했다.

```text
n = 1

1
```

```text
n = 2

[1] 2 [1]
```

```text
n = 3

[1 2 1] 3 [1 2 1]
```

---

# n = 4 예상

같은 규칙을 적용하면:

```text
1 2 1 3 1 2 1 4 1 2 1 3 1 2 1
```

즉:

```text
[n=3의 이동]
4
[n=3의 이동]
```

구조가 된다.

좀 더 일반화하면:

```text
[n-1개의 원판 이동]
n번 원판 이동
[n-1개의 원판 이동]
```

이다.

여기서 재귀적인 구조를 발견했다.

---

# 처음 발견한 홀짝 규칙

시뮬레이션하면서 `n`의 홀짝에 따라 가장 작은 원판의 첫 이동 방향이 달라지는 것도 발견했다.

```text
n이 홀수

1번 원판:
1 → 3
```

```text
n이 짝수

1번 원판:
1 → 2
```

이 규칙을 이용해서 반복문으로 시뮬레이션하는 것도 가능하다.

하지만 문제를 더 살펴보니 이 홀짝을 직접 판별하지 않아도 되는 더 일반적인 구조가 있었다.

---

# 가장 중요한 사고 전환

원판 `n`개를:

```text
from → to
```

로 이동한다고 생각한다.

가장 큰 `n`번 원판을 `from → to`로 옮기려면 그 위의 원판들이 없어야 한다.

따라서 먼저:

```text
n-1개의 원판을

from → via
```

로 옮겨야 한다.

그러면 가장 큰 원판을:

```text
from → to
```

로 이동할 수 있다.

마지막으로 `via`에 있던 작은 원판들을:

```text
via → to
```

로 이동한다.

결국 전체 문제는:

```text
1. n-1개 : from → via

2. n번   : from → to

3. n-1개 : via → to
```

로 분해된다.

---

# n = 3으로 확인

목표:

```text
원판 3개를 1 → 3
```

그러면:

```text
① 원판 2개
   1 → 2

② 원판 3
   1 → 3

③ 원판 2개
   2 → 3
```

이다.

그런데:

```text
원판 2개를 1 → 2
```

라는 작업 역시 똑같은 하노이 탑 문제다.

다시 나누면:

```text
원판 1개 : 1 → 3
원판 2   : 1 → 2
원판 1개 : 3 → 2
```

이다.

즉 큰 문제를 해결하는 과정에서 **동일한 형태의 작은 문제가 반복된다.**

---

# 재귀 함수에 필요한 상태

처음에는 Stack 3개의 전체 상태가 필요하다고 생각했다.

하지만 실제 정답을 생성하는 데 필요한 것은:

```text
n    = 이동해야 할 원판 개수
from = 출발 기둥
to   = 목적지 기둥
via  = 보조 기둥
```

뿐이었다.

따라서 함수 자체를:

```java
move(n, from, to, via)
```

라는 의미로 만들 수 있다.

이 함수의 의미는:

```text
n개의 원판을
from에서 to로
via를 이용해서 옮긴다.
```

이다.

---

# 재귀 구조

`move(n, from, to, via)`를 실행한다면:

```text
move(n - 1, from, via, to)

[from → to] 기록

move(n - 1, via, to, from)
```

이라는 구조가 된다.

중요한 것은 각 재귀 호출에서:

```text
from
to
via
```

의 **역할이 바뀐다는 것**이다.

---

# 처음 작성했던 재귀

처음에는 다음과 비슷하게 생각했다.

```java
int[][] move(int n, int from, int to, int via) {

    int[][] answer = {
        {from, to},
        {from, via},
        {to, via}
    };

    if (n == 1) return answer;

    return move(n - 1, to, via, from);
}
```

여기에는 두 가지 문제가 있었다.

---

## 문제 1. n = 1인데 3개의 이동을 반환

원판이 하나라면 필요한 이동은:

```text
from → to
```

하나뿐이다.

그런데:

```java
{
    {from, to},
    {from, via},
    {to, via}
}
```

를 반환하면 이동을 3개 생성한다.

---

## 문제 2. 재귀가 한 번만 존재

하노이의 구조는:

```text
n-1 이동

n 이동

n-1 이동
```

이다.

따라서 `n-1` 문제는 한 번이 아니라 **두 번 등장한다.**

---

# List를 사용한 이유

처음에는 재귀 함수가 매번:

```java
int[][]
```

을 반환하도록 생각했다.

하지만 구조를 보면:

```text
첫 번째 재귀의 여러 이동
+
현재 이동 하나
+
두 번째 재귀의 여러 이동
```

을 계속 합쳐야 한다.

매번 배열을 새로 만들고 합치는 것보다:

```java
List<int[]> answer
```

하나를 공유하고 이동이 발생할 때마다:

```java
answer.add(new int[]{from, to});
```

하는 것이 훨씬 단순하다.

즉 재귀 함수는:

```text
결과를 만들어 반환한다
```

보다:

```text
정답 List에 현재 이동을 기록한다
```

라는 역할을 가지게 된다.

---

# 종료 조건

최종적으로:

```java
if (n == 0) {
    return;
}
```

형태의 종료 조건을 사용할 수 있다.

`n = 1`이라면:

```text
move(1)

↓ 첫 번째 재귀

move(0)
→ 종료

↓ 현재 원판 이동

from → to 기록

↓ 두 번째 재귀

move(0)
→ 종료
```

가 된다.

따라서 원판 하나일 때 자연스럽게:

```text
[from, to]
```

한 번만 기록된다.

---

# 재귀 호출 흐름

예를 들어:

```text
move(3, 1, 3, 2)
```

라면:

```text
move(3, 1, 3, 2)

├─ move(2, 1, 2, 3)
│
│  ├─ move(1, 1, 3, 2)
│  │  └─ 1 → 3
│  │
│  ├─ 1 → 2
│  │
│  └─ move(1, 3, 2, 1)
│     └─ 3 → 2
│
├─ 1 → 3
│
└─ move(2, 2, 3, 1)

   ├─ move(1, 2, 1, 3)
   │  └─ 2 → 1
   │
   ├─ 2 → 3
   │
   └─ move(1, 1, 3, 2)
      └─ 1 → 3
```

따라서 최종 이동:

```text
[1, 3]
[1, 2]
[3, 2]
[1, 3]
[2, 1]
[2, 3]
[1, 3]
```

이 생성된다.

---

# Stack이 결국 필요하지 않았던 이유

처음에는 다음 상태를 모두 관리하려고 했다.

```text
Stack 1의 현재 상태
Stack 2의 현재 상태
Stack 3의 현재 상태
```

그리고 매 이동마다:

```text
pop
peek
이동 가능 여부 확인
push
```

를 수행하려고 했다.

하지만 재귀 구조 자체가 하노이 탑의 규칙을 만족하는 이동만 생성한다.

따라서:

```text
이 원판을 여기 놓아도 되는가?
```

를 매번 검사할 필요가 없다.

정답 생성에 필요한 상태는 실제로:

```text
n
from
to
via
```

뿐이었다.

이전 문제들과 마찬가지로:

> 실제 문제의 모든 상태를 프로그램에서 그대로 저장할 필요는 없다.

라는 점이 중요했다.

---

# 홀짝 판별도 필요하지 않았던 이유

처음에는:

```text
n 홀수
→ 작은 원판을 1 → 3

n 짝수
→ 작은 원판을 1 → 2
```

라는 패턴을 발견했다.

패턴 자체는 맞지만 재귀 풀이에서는 이를 직접 사용할 필요가 없다.

왜냐하면 각 재귀 호출에서:

```text
from
to
via
```

의 역할을 바꾸는 것만으로 필요한 이동 방향이 자연스럽게 결정되기 때문이다.

즉:

```text
홀짝에 따라 이동 방향을 직접 계산
```

하는 것보다:

```text
현재 문제를 더 작은 동일한 문제로 분해
```

하는 것이 더 일반적인 해결 방법이었다.

---

# 이동 횟수

직접 확인한 이동 횟수:

```text
n = 1 → 1
n = 2 → 3
n = 3 → 7
n = 4 → 15
```

`n`개의 원판을 옮기는 횟수를 `T(n)`이라고 하면:

```text
T(n) = T(n-1) + 1 + T(n-1)
```

즉:

```text
T(n) = 2T(n-1) + 1
```

이다.

그리고:

```text
T(1) = 1
```

이므로:

```text
T(n) = 2^n - 1
```

이 된다.

---

# 시간복잡도

실제로 만들어야 하는 이동 자체가:

```text
2^n - 1
```

개다.

따라서 시간복잡도는:

```text
O(2^n)
```

이다.

이 문제에서는 결과 자체의 크기가 `2^n - 1`이므로 이보다 본질적으로 빠르게 모든 이동을 반환할 수는 없다.

---

# 최대 입력에서 실제 연산량

제한:

```text
n ≤ 15
```

따라서 최대 이동 횟수:

```text
2^15 - 1
= 32767
```

즉 최대 약 3만 2천 개의 이동을 생성한다.

충분히 처리 가능한 크기다.

---

# 공간복잡도

정답으로 저장해야 하는 이동:

```text
2^n - 1
```

개이므로 결과 저장 공간은:

```text
O(2^n)
```

이다.

재귀 호출 깊이는:

```text
n
```

이므로 호출 스택 자체는:

```text
O(n)
```

이다.

따라서 정답 배열까지 포함한 전체 공간은:

```text
O(2^n)
```

으로 볼 수 있다.

# 이번 문제에서 잘한 점

## 1. Stack이라는 자연스러운 모델부터 시작했다

문제를 보자마자:

```text
기둥 = Stack
```

이라는 구조를 생각했다.

실제 퍼즐 상태를 표현한다는 관점에서는 정확한 모델링이었다.

---

## 2. 작은 입력을 직접 시뮬레이션했다

바로 코드를 작성하는 대신:

```text
n = 1
n = 2
n = 3
n = 4
```

의 원판 이동을 직접 확인했다.

그 결과:

```text
1

1 2 1

1 2 1 3 1 2 1

1 2 1 3 1 2 1 4 1 2 1 3 1 2 1
```

이라는 패턴을 직접 발견했다.

이 과정이 재귀 구조를 찾는 핵심이었다.

---

## 3. 홀짝 규칙까지 관찰했다

작은 원판의 이동 방향이 `n`의 홀짝에 따라 달라진다는 것도 직접 발견했다.

최종 풀이에서는 필요하지 않았지만 문제의 동작을 제대로 관찰하고 있었다는 의미가 있다.

---

## 4. 큰 문제 안에서 작은 동일 문제를 발견했다

가장 중요한 부분.

```text
n개의 원판을 이동
```

하는 문제를:

```text
n-1개의 원판 이동
+
가장 큰 원판 이동
+
n-1개의 원판 이동
```

으로 분해했다.

이것이 그대로 재귀 함수 구조가 되었다.

---

# 개선할 점

## 1. 자료구조와 알고리즘을 구분하기

처음:

```text
하노이 탑 → Stack 같다 → Stack으로 풀자
```

라고 생각했다.

하지만:

```text
문제를 표현하기 좋은 자료구조
```

와:

```text
정답을 계산하기 좋은 알고리즘
```

은 다를 수 있다.

Stack은 하노이 탑의 상태를 표현하기에는 좋지만 이번 문제의 최소 이동 순서를 구하는 데 반드시 필요한 것은 아니었다.

앞으로 자료구조가 떠오르면:

```text
이 자료구조가 문제를 표현하기 좋은 것인가?

아니면 실제로 정답을 계산하기 위해 필요한 것인가?
```

를 구분한다.

---

## 2. 시뮬레이션 전에 반복되는 작은 문제 찾기

이번에는 Stack 시뮬레이션을 생각한 뒤 패턴을 발견했다.

앞으로는 문제를 보면서:

```text
큰 문제를 해결하기 전에
같은 형태의 작은 문제를 먼저 해결해야 하는가?
```

도 확인한다.

이번 문제에서는:

```text
n개를 이동하려면
n-1개를 먼저 이동해야 한다.
```

가 강한 재귀 신호였다.

## 3. 재귀에서는 함수의 의미를 먼저 정의하기

재귀 코드를 바로 작성하면 매개변수 순서가 쉽게 꼬인다.

실제로 이번에도:

```java
move(n - 1, from, to, via);
```

처럼 처음 재귀 호출의 목적지를 잘못 전달했다.

코드보다 먼저:

```text
move(n, from, to, via)

= n개의 원판을
  from에서 to로
  via를 이용하여 옮긴다.
```

라고 함수의 의미를 문장으로 정의하면 훨씬 쉽다.

그다음:

```text
move(n-1, from, via, to)
[from, to]
move(n-1, via, to, from)
```

으로 역할을 대입하면 된다.

# 재귀 문제를 만났을 때 체크할 것

앞으로 재귀 가능성이 있는 문제에서는 다음을 확인한다.

```text
1. 큰 문제와 동일한 형태의 작은 문제가 존재하는가?

2. n을 줄이면 같은 문제로 표현되는가?

3. 가장 작은 문제는 무엇인가?
   → 종료 조건

4. 작은 문제의 답을 이용해서
   현재 문제의 답을 어떻게 구성하는가?

5. 재귀 함수 하나의 역할을
   한 문장으로 설명할 수 있는가?

6. 각 매개변수가 재귀 호출에서
   어떤 역할로 바뀌는가?
```

# 오늘의 핵심 교훈

이번 문제에서 가장 중요한 변화:

```text
처음:

현재 Stack 상태가 무엇이지?
어떤 원판을 움직일 수 있지?
어디로 움직여야 하지?

↓

최종:

n개의 원판을 옮기려면
n-1개의 원판을 먼저 옮겨야 한다.
```

즉 현재 상태를 하나씩 따라가는 것보다:

```text
큰 문제를 해결하기 위해
어떤 작은 문제를 먼저 해결해야 하는가?
```

를 보는 것이 훨씬 단순했다.

# 한 줄 복기

```text
하노이 탑의 전체 Stack 상태를 시뮬레이션하지 말고,
n개 이동을
(n-1개 이동) + (가장 큰 원판 이동) + (n-1개 이동)
으로 분해하여 동일한 문제를 재귀적으로 해결한다.
```

# 개인적으로 가져갈 사고 패턴

이번 문제에서 가장 가져갈 만한 질문:

> "이 문제 안에 크기만 작은 똑같은 문제가 들어있는가?"

있다면:

```text
큰 문제
↓
작은 동일 문제
↓
더 작은 동일 문제
↓
종료 조건
```

으로 내려갈 수 있는지 확인한다.

특히 다음과 같은 형태가 보이면 재귀를 의심한다.

```text
n을 처리하기 위해 n-1을 먼저 처리한다.

현재 작업 하나를 수행한다.

다시 n-1 형태의 작업을 수행한다.
```

그리고 재귀 구현 전에 반드시:

```text
이 함수가 정확히 무엇을 하는 함수인가?
```

를 한 문장으로 먼저 정의한다.

이번 문제에서는:

```text
move(n, from, to, via)

= n개의 원판을 from에서 to로
  via를 이용해서 이동시키고
  이동 기록을 answer에 추가한다.
```

이 정의 하나가 재귀 호출의 인자 순서까지 결정한다.
