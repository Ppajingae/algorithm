# Day 4 - 덧칠 풀이 복기

## 결과

- 풀이 성공
- 핵심 유형: 그리디 / 정렬된 배열 순회 / 상태 추적
- 목표 시간복잡도: `O(section.length)`
- 핵심 아이디어:
    - 벽 전체를 관리할 필요가 없다.
    - 이미 칠한 모든 구역을 저장할 필요도 없다.
    - **현재 롤러로 어디까지 칠했는지만 기억하면 된다.**

---

# 처음 접근

처음에는 각 구역이 칠해졌는지를 관리하기 위해 다음과 같은 구조를 생각했다.

```java
Map<Integer, Boolean> map = new HashMap<>();

for (int i : section) {
    map.put(i, false);
}
```

예를 들어:

```text
section = [2, 3, 6]
```

이라면:

```text
2 → false
3 → false
6 → false
```

로 만들고 롤러가 지나간 위치를:

```text
2 → true
3 → true
6 → false
```

처럼 변경하는 방식이었다.

하지만 여기서 문제가 생겼다.

---

# 첫 번째 문제점 - Map이 필요하지 않았다

최종적으로 필요한 것은:

```text
각 구역이 칠해졌는가?
```

라는 모든 상태가 아니었다.

`section`이 이미 오름차순으로 정렬되어 있기 때문에 왼쪽부터 확인하면서:

```text
현재 section이 이미 칠해져 있는가?
```

만 판단하면 된다.

따라서 필요한 상태는:

```text
현재 롤러가 어디까지 칠했는가?
```

하나뿐이다.

즉:

```text
Map<Integer, Boolean>
```

전체를 관리할 필요 없이:

```text
rollerLocation
```

같은 하나의 변수로 상태를 표현할 수 있다.

---

# 두 번째 문제점 - 벽 전체를 탐색할 필요가 없었다

처음에는:

```java
for (; minValue <= maxValue; minValue++) {
    ...
}
```

형태로 가장 작은 `section`부터 가장 큰 `section`까지 모든 벽의 위치를 확인했다.

예를 들어:

```text
section = [1, 100000]
```

이면 실제로 관심 있는 위치는:

```text
1
100000
```

두 곳뿐이다.

그런데 벽을 기준으로 탐색하면:

```text
1
2
3
4
...
99999
100000
```

을 모두 확인하게 된다.

문제에서 이미 필요한 위치만:

```text
section
```

으로 제공하고 있기 때문에 벽 전체를 탐색할 필요가 없다.

따라서:

```java
for (int i = 0; i < section.length; i++) {
    ...
}
```

처럼 `section`만 탐색하는 것이 더 자연스럽다.

---

# 세 번째 문제점 - 롤러를 사용한 시점과 횟수 증가 시점

처음에는 롤러가 `m`칸을 모두 이동한 뒤:

```java
if (count == m) {
    answer++;
}
```

로 횟수를 증가시키려고 했다.

하지만 실제 의미는 다르다.

아직 칠하지 않은 구역을 발견해서:

```text
여기서 롤러를 사용해야겠다.
```

라고 결정한 순간 이미 롤러를 **한 번 사용한 것**이다.

따라서 중요한 것은:

```text
m칸을 하나씩 이동했는가?
```

가 아니라:

```text
새로운 롤러 사용이 필요한가?
```

이다.

---

# 최종적으로 필요한 상태

결국 필요한 값은 매우 단순하다.

```text
answer
→ 롤러를 사용한 횟수

rollerLocation
→ 현재까지 롤러로 칠해진 마지막 위치
```

그리고 `section`을 왼쪽부터 확인한다.

```text
현재 section <= rollerLocation

→ 이미 칠해진 구역
→ 넘어감
```

반대로:

```text
현재 section > rollerLocation

→ 아직 칠하지 않은 구역
→ 새로운 롤러 필요
```

새로운 롤러를 사용했다면:

```text
현재 section부터 길이 m만큼 칠한다.
```

그리고 새로운 `rollerLocation`을 계산하면 된다.

---

# 예제 흐름

```text
n = 8
m = 4
section = [2, 3, 6]
```

처음:

```text
rollerLocation = 0
answer = 0
```

---

## section = 2

```text
2 > rollerLocation
```

아직 칠하지 않은 곳이다.

따라서 `2`에서 롤러를 사용한다.

```text
2 3 4 5
────────
```

현재 칠해진 마지막 위치:

```text
rollerLocation = 5
```

롤러 사용 횟수:

```text
answer = 1
```

---

## section = 3

현재:

```text
section = 3
rollerLocation = 5
```

따라서:

```text
3 <= 5
```

이미 첫 번째 롤러에 의해 칠해졌다.

아무것도 하지 않고 넘어간다.

---

## section = 6

현재:

```text
section = 6
rollerLocation = 5
```

따라서:

```text
6 > 5
```

아직 칠하지 않은 곳이다.

새로운 롤러를 사용한다.

```text
6 7 8 ...
────────
```

롤러 사용 횟수:

```text
answer = 2
```

따라서 최종 결과:

```text
2
```

# 잘한 점

## 1. `n`이 정말 필요한지 의심함

문제에서:

```java
solution(int n, int m, int[] section)
```

으로 `n`이 주어지지만 풀이 과정에서:

```text
n을 반드시 사용해야 하나?
```

라는 의문을 가졌다.

좋은 접근이었다.

최소 롤러 사용 횟수를 계산하기 위해 중요한 정보는:

```text
벽 전체 길이
```

가 아니라:

```text
다시 칠해야 하는 구역들의 위치
```

이다.

따라서 실제 횟수 계산에서는 `n`을 사용하지 않아도 해결할 수 있다.

### 가져갈 점

> 문제에서 매개변수로 주어졌다고 해서 모든 값을 반드시 사용할 필요는 없다.

---

## 2. 처음부터 `section`의 위치 관계를 이용하려고 함

처음부터:

```text
section 값들의 차이를 이용할 수 있지 않을까?
```

라는 생각을 했다.

방향 자체는 좋았다.

다만 단순히:

```text
현재 section - 이전 section
```

만 비교하면 안 된다.

예를 들어:

```text
m = 4
section = [2, 5, 8]
```

이면:

```text
5 - 2 = 3
8 - 5 = 3
```

이지만 한 번의 롤러로 `[2, 5, 8]`을 모두 칠할 수는 없다.

비교해야 하는 것은:

```text
이전 section
```

이 아니라:

```text
현재 롤러가 마지막으로 칠한 위치
```

였다.

그래도 **위치 차이를 이용하면 되지 않을까?**라고 생각한 방향은 최종 풀이와 상당히 가까웠다.

---

## 3. 시간 초과 후 구조를 단순화함

처음에는:

```text
Map
min
max
count
벽 전체 순회
```

등 여러 상태가 있었다.

풀이를 다시 생각하면서 결국:

```text
section 한 번 순회
+
rollerLocation 하나
```

까지 줄였다.

이런 식으로 풀이가 단순해지는 과정은 중요하다.

```text
상태가 너무 많다
    ↓
정말 필요한 정보가 무엇인지 다시 생각
    ↓
최소한의 상태만 유지
```

라는 흐름을 기억해둘 만하다.

---

## 4. 정렬되어 있다는 조건을 활용함

문제에서:

```text
section은 오름차순으로 정렬되어 있다.
```

라고 보장한다.

이 조건 덕분에 왼쪽부터 한 번만 탐색하면서:

```text
이미 칠해진 곳 → 무시
아직 안 칠해진 곳 → 새 롤러
```

라는 판단이 가능하다.

이미 지나간 `section`을 다시 확인할 필요가 없다.

이게 최종적으로 `O(N)` 풀이가 가능한 이유다.

# 개선해야 할 점

## 1. 자료구조를 먼저 선택하지 않기

처음에는:

```java
Map<Integer, Boolean>
```

으로 각 section의 상태를 관리하려고 했다.

하지만 Map을 만든 다음 실제 로직에서는:

```java
map.put(section, true);
```

로 값을 변경할 뿐, 그 상태를 핵심 판단에 제대로 활용하지 않았다.

이럴 때는:

> 이 자료구조가 없으면 정말 문제를 풀 수 없는가?

를 생각해보는 것이 좋다.

이번 문제에서는:

```text
Map 필요 없음
List 필요 없음
Set 필요 없음
```

이고 단순한 정수 변수 하나면 충분했다.

### 체크 포인트

```text
자료구조를 선택한다
        ↓
무엇을 저장할 것인가?
        ↓
왜 저장해야 하는가?
        ↓
나중에 이 값을 어떻게 사용할 것인가?
```

마지막 질문에 답하기 어렵다면 불필요한 상태일 가능성이 있다.

---

## 2. 배열의 index와 실제 값을 구분하기

중간 코드에서:

```java
rollerLocation = j + i;
```

를 사용했다.

하지만:

```text
i
```

는 `section` 배열의 **index**이고:

```text
section[i]
```

는 실제 벽의 **구역 번호**이다.

예를 들어:

```text
section = [2, 3, 6]

i = 0
section[i] = 2
```

이다.

따라서 좌표나 실제 위치를 계산할 때:

```text
배열의 index인가?
실제 저장된 값인가?
```

를 명확하게 구분해야 한다.

이 실수는 코테에서 꽤 자주 발생할 수 있다.

---

## 3. 내부 반복문이 정말 필요한지 확인하기

중간 풀이에서는 롤러가 칠하는 `m`개의 구역을 직접 계산하기 위해:

```java
for (int j = 0; j < m; j++) {
    ...
}
```

를 사용했다.

하지만 실제로 필요한 것은:

```text
롤러가 지나가는 모든 위치
```

가 아니라:

```text
롤러가 마지막으로 칠하는 위치
```

하나뿐이다.

따라서 중간 과정을 하나씩 계산할 필요가 없다.

### 앞으로 확인할 것

반복문을 작성했을 때:

```text
이 반복문의 최종 목적이 무엇인가?
```

를 생각한다.

만약 최종적으로 숫자 하나를 계산하기 위한 반복이라면:

```text
수식으로 바로 계산할 수 없는가?
```

를 확인해본다.

이건 최근 연습하고 있는 **시간복잡도 개선**과 직접 연결된다.

# 왜 그리디가 가능한가?

아직 칠하지 않은 가장 왼쪽 구역이 있다고 생각한다.

```text
section[i]
```

이 구역은 반드시 칠해야 한다.

그렇다면 롤러를 사용할 때 이 구역을 포함하면서 가능한 한 오른쪽까지 칠하는 것이 유리하다.

```text
section[i]
↓
# . . . . ...
─────────→
   m칸
```

왼쪽 영역은 이미 처리했기 때문에 다시 왼쪽을 많이 포함하도록 롤러를 배치할 이유가 없다.

따라서:

```text
가장 왼쪽의 아직 안 칠한 구역 발견
        ↓
그 위치부터 롤러 사용
        ↓
가능한 오른쪽까지 칠함
        ↓
다음 section 확인
```

을 반복하면 된다.

현재 순간의 최선의 선택이 이후 선택을 방해하지 않기 때문에 그리디 방식으로 해결할 수 있다.

---

# 시간복잡도

`section`을 한 번만 탐색한다.

```text
section.length = K
```

라고 하면:

```text
O(K)
```

이다.

최대:

```text
K = 100,000
```

이므로 충분히 빠르다.

추가적인 Map이나 배열도 필요하지 않으므로 추가 공간복잡도는:

```text
O(1)
```

로 해결할 수 있다.

---

# 이번 문제의 시간복잡도 개선 과정

처음 생각:

```text
벽의 각 위치를 탐색
+
Map으로 칠했는지 관리
```

↓

개선:

```text
칠해야 하는 위치는 이미 section에 들어 있음
```

↓

다시 개선:

```text
section은 이미 정렬되어 있음
```

↓

따라서:

```text
section을 왼쪽부터 한 번만 탐색
```

↓

그리고:

```text
각 구역의 칠함/안 칠함을 저장할 필요 없음
```

↓

최종적으로:

```text
현재 어디까지 칠했는지만 저장
```

결과:

```text
O(section.length)
공간 O(1)
```

처음에는:

```text
어떤 구역들이 칠해졌는가?
```

를 관리하려고 했다.

하지만 실제로 필요한 질문은:

```text

```

였다.

즉 여러 개의 boolean 상태를 관리하는 문제를:

```text

```

라는 **경계값 하나를 관리하는 문제**로 바꿀 수 있었다.

이 패턴은 다른 문제에서도 꽤 중요하다.

```text

        ↓

특정 경계값 하나로
상태 전체를 표현할 수 있나?
```

를 생각해볼 것.

# 오늘 가져갈 포인트

> **모든 상태를 저장하지 말고, 상태를 표현할 수 있는 최소한의 값이 무엇인지 찾는다.**

이번 문제에서는:

```text
Map<구역, 칠했는지>
```

가 아니라:

```text
현재까지 칠해진 마지막 위치
```

하나면 충분했다.

그리고 정렬된 `section`을 이용해:

```text
이미 칠해진 범위 → skip
범위 밖 → 새로운 롤러
```

만 판단하면 됐다.
